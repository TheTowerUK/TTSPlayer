# ADR-019: Diagnostics Export and Support Strategy

**Status:** Proposed  
**Date:** 2026-07-16  
**Milestone:** M4 Phase 4.6  
**Authors:** M4 documentation pass

---

## Context

Phase 4.6 adds a read-only Diagnostics screen (ADR-017) backed by `RuntimeDiagnosticsSnapshot` (ADR-018). Users and maintainers need to share runtime context when troubleshooting catalogue, provider, cache, or playback issues — especially on Windows desktop against a TNAS HTTPS deployment.

Requirements:

- Copy-friendly for email or chat support
- No automatic upload or remote telemetry (product principles)
- No passwords, tokens, certificate files, or personal media paths
- Stable format testable in CI
- Clearly separated from editable Settings

Open questions from [diagnostics.md](../diagnostics.md) planning: plain text vs JSON, log ring buffer, TNAS deploy hints.

---

## Decision

### 1. Primary export format: plain text

`DiagnosticsService.formatExport(RuntimeDiagnosticsSnapshot)` produces UTF-8 plain text with:

```
TTSPlayer Diagnostics
Captured: 2026-07-16T20:15:00.000Z
App: 0.5.0-dev (build 42) — windows

=== Application ===
...

=== Provider ===
...

=== Catalogue ===
...

=== Cache ===
...

=== Search ===
...

=== Playback ===
...

=== Library ===
...
```

**Rules:**

- Fixed section order matching ADR-018 DTOs
- Fixed heading strings (test golden prefixes)
- Missing sections render `Unavailable` lines — never omit headings
- Duration and byte values use human-readable units in export (e.g. `12.4 MB`, `3m 12s`)

**JSON export:** Out of scope for 4.6 v1. Revisit only if programmatic parsing becomes a support requirement.

### 2. Delivery mechanisms

| Action | Platform | Behaviour |
|---|---|---|
| **Copy to clipboard** | All | Primary action on Diagnostics screen; full `formatExport()` text |
| **Save to file** | Windows (optional 4.6) | `FilePicker` or default `ttsplayer-diagnostics-YYYYMMDD-HHMMSS.txt` in Downloads |
| **Share sheet** | Future mobile | Deferred |

Copy success: brief `SnackBar` confirmation. Failure: retry message — not a blocking dialog.

### 3. Redaction and safety (export = on-screen)

Export uses the **same redacted fields** as the UI (ADR-018). Additional export rules:

- No `file_path`, `thumbnail_path`, `root_path`, or full media URLs
- HTTPS rows: host + port only
- Provider errors: user-readable `remote_fetch_errors` text — no certificate PEM, no stack traces
- Playback: item id + title — no resolver URI

Footer line (optional):

```
---
Generated by TTSPlayer Diagnostics. Do not edit section headings.
```

### 4. Reset diagnostic counters

**Not offered in 4.6 v1.**

`indexBuildCount` and `cacheEvictionCount` are lifetime session diagnostics with existing semantics from Phase 4.5 tests. Reset would require new APIs and risks confusing support correlation. Revisit only with explicit product request.

### 5. Log ring buffer

**Deferred.**

Including last N `debugPrint` lines requires new in-app log collection infrastructure — duplicate of IDE/device logs and out of "consume existing instrumentation" scope.

### 6. TNAS / HTTPS hints

When provider health is `failed` and error text matches TLS/network patterns (`remote_fetch_errors` classification):

- Diagnostics screen may show a **read-only hint** linking to [TNAS deploy checklist](../../deployment/tnas-caddy-deploy-checklist.md) (in-app `url_launcher` or copyable URL)
- Hint is not included automatically in export unless user copies full screen context — export stays factual snapshot only

### 7. Settings separation (ADR-005)

- Entry: Settings → **Diagnostics & Advanced** → **View diagnostics**
- Diagnostics screen has no save/apply/reset-settings actions
- Version string remains on Settings section; Diagnostics repeats version inside Application section for export completeness

---

## Rationale

- Plain text pastes cleanly into support tickets without JSON escaping.
- Clipboard-first avoids file-permission complexity on all platforms; Windows save is optional enhancement.
- Deferring log buffer and counter reset keeps 4.6 focused on exposing existing state.
- Single redaction path for UI and export prevents leakage via copy.

---

## Consequences

### Positive

- Support workflow: reproduce issue → open diagnostics → copy → send.
- Stable headings enable widget/integration tests without brittle full-string goldens.

### Negative

- Plain text is harder to machine-parse than JSON.
- No historical snapshots — only current point-in-time.

### Neutral

- User must manually share export; no privacy concern from automatic upload.

---

## Alternatives considered

| Alternative | Rejected because |
|---|---|
| JSON primary | Poor paste experience; secrets harder to audit visually |
| Automatic email/upload | Violates local-first; privacy risk |
| Export includes full catalogue paths | Personal data leakage |
| Reset counters button | No production counter reset semantics yet |
| Include debug log ring | New infrastructure; not existing instrumentation |
