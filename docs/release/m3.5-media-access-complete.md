## Summary

M3.5 delivers a **provider-neutral media access architecture**. The client no longer assumes a single storage backend. Catalogue paths remain filesystem truth; playback and artwork resolve them at consumption boundaries through one abstraction.

The project evolved from *“play files from a specific path”* to *“resolve media from any supported provider through a single abstraction.”*

---

## Delivered

- Provider-neutral media access architecture ([spec](../architecture/media-access-abstraction.md))
- `MediaLocationResolver` with local and HTTP serving providers
- Playback integration (`PlaybackService.play()`)
- Artwork integration (`ArtworkImage` load path)
- Canonical path mapping specification ([path-mapping.md](../architecture/path-mapping.md))
- Caddy reference serving layer (`backend/caddy.config`, deployment docs)
- Comprehensive resolver and integration unit tests

## Architecture

```
Storage source
    ↓
Media access provider
    ↓
MediaLocationResolver
    ↓
Playback / Artwork
```

### Supported provider types

| Provider | Example catalogue path | Resolver output |
|---|---|---|
| Local filesystem | `D:\Media\Videos\a.mp4` | `file://` URI |
| Windows mapped drive | `Y:\Media\Videos\a.mp4` | `file://` on desktop; HTTP when configured |
| UNC / SMB | `\\NAS\Media\Videos\a.mp4` | `file://` on desktop; HTTP when configured |
| HTTP serving layer | (same fs path in catalogue) | `https://host/media/...` |
| NAS reference deployment | TNAS + Caddy | HTTP via configured base URL |

TNAS + Caddy is a **reference HTTP provider**, not a hard dependency of the core architecture.

## Exit criteria before Phase 4

Complete these operational validations before opening **Phase 4 — Network Catalogue & Provider Configuration**.

### 1. Windows regression (required)

→ Full checklist: [Windows Regression Checklist](#windows-regression-checklist) below.

If all items pass, the abstraction has proven transparent on desktop.

### 2. TNAS validation (parallel)

Complete the [TNAS Caddy deploy checklist](../deployment/tnas-caddy-deploy-checklist.md):

- [ ] `GET /catalog.json` → **200**
- [ ] `GET /media/...` → **200**
- [ ] `Range: bytes=0-1023` → **206**
- [ ] HTTP playback smoke test (optional until Phase 4 wiring)

This validates the HTTP serving provider independently of Flutter catalogue loading.

## Phase 4 preview

Once exit criteria are met, the cycle continues with **Phase 4 — Network Catalogue & Provider Configuration**:

- HTTP-backed catalogue loading
- User-configurable media providers (Local, SMB, HTTP)
- Provider preference and fallback logic
- Runtime configuration UI
- Optional automatic provider discovery (future)

Phase 4 is **configurable media access**, not “NAS support” — the NAS is one supported provider among others.
