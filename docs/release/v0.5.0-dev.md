## Phase retrospectives

Short notes captured at phase closure — what worked and what to carry forward. Added after each completed M4 sub-phase.

### Phase 4.1 — Provider Management (2026-07-12)

**What went well**

- Observability layer added on top of the existing M3.5 provider chain — no rewrite of media access or catalogue loading.
- ADR-001–003 drew a clear line between operational provider status (dashboard) and configuration (deferred to 4.2), avoiding duplicated UI.
- Windows runtime V1–V10 covered local preferred, HTTPS fallback, degraded load, demo fallback, `httpRequired`, failed refresh retention, TLS errors, and indexer integration.
- M3.5 provider order and last-good catalogue semantics unchanged — no behavioural regressions in the selection chain.
- Provider Status panel replaced the legacy Storage Status section with consistent health vocabulary and refresh actions.

**Lessons**

- Spec-first delivery with ADRs accepted before coding kept a naturally bounded scope (instrumentation + UI, not new provider types).
- Incremental `CatalogService` instrumentation was lower risk than introducing a parallel status service.
- The opt-in Windows runtime harness (`PHASE_41_RUNTIME`) proved worth keeping — it became the template for 4.2 closure.
- Constrained-height dashboard scroll tests caught layout issues before manual smoke.

→ [Validation results](../roadmap/m4-phase-4.1-provider-management.md#windows-runtime-validation-2026-07-12)

### Phase 4.2 — Settings Framework (2026-07-12)

**What went well**

- Repository architecture introduced cleanly — `SettingsRepository` as persistence-only, runtime services consuming snapshots.
- Legacy migration from `media_provider_config_v1` completed without regression; dual-read transition preserved upgrades.
- Windows validation matched automated tests — closure S1–S13 aligned with unit/widget coverage.
- No behavioural regressions — provider lifecycle (4.1), catalogue refresh semantics, and dashboard Provider Status unchanged.
- Incremental commits (envelope → shell → provider integration → timeout) kept each step reviewable.

**Lessons**

- Repository-first implementation reduced risk — persistence and migration landed before UI integration.
- Smaller, focused commits simplified review and made rollback straightforward.
- Runtime validation harnesses are worth keeping for future phases (`PHASE_42_RUNTIME` mirrors 4.1).
- Evolving the existing provider form into a grouped settings screen was faster and safer than rebuilding configuration from scratch.

→ [Validation results](../roadmap/m4-phase-4.2-settings-framework.md#windows-runtime-validation-2026-07-12)

### Phase 4.3 — Library Experience (2026-07-13)

**What went well**

- Repository-first delivery (metadata → catalogue helpers → sort/filter domain → UI consumers) kept each step reviewable and matched the 4.2 cadence.
- Immutable catalogue discipline held across sort, filter, favourites, breadcrumbs, and search presentation — no accidental catalogue mutation.
- Catalogue hierarchy helpers (`ancestorChainForFolder`, `parentFolderOfItemId`) unified breadcrumbs, search context, and favourites resolution without path parsing.
- Opt-in Windows runtime harness (`PHASE_43_RUNTIME`) covered L1–L25 including production local + HTTPS catalogues.
- Search presentation improved without touching `SearchService` scoring or index build.

**Lessons**

- Lightweight library grouping (headers only when multiple libraries match) was clearer than always-flat or deeply nested grouping.
- Shared `EmptyState` with scroll-safe layout reduced duplication and caught 900×420 overflow early.
- Widget-test keyboard shortcuts (Escape) need explicit focus setup — validate clear-button and Enter in harness; confirm Escape manually on Windows.
- Filter-empty state requires a leaf folder with no visible subfolders after filter — document the `view.isEmpty` contract when writing harness scenarios.

→ [Validation results](../roadmap/m4-phase-4.3-library-experience.md#windows-runtime-validation-2026-07-13)

### Phase 4.4 — Playback Improvements (2026-07-14)

**User-visible deliverables**

- Default playback speed in Settings (Windows; read-only display on unsupported platforms)
- In-player speed menu (0.5×–2.0×) with session override; Watch Again retains current session settings
- Embedded audio and subtitle track menus when the file exposes tracks (Windows)
- Consolidated player popups with focus-aware keyboard shortcuts and Esc-closes-popup-first behaviour
- Auto-hide controls resume after popup dismissal
- Resolver-aware fatal error copy with **Try Again** retry; rate and track failures remain non-fatal
- Resume, progress, completion, and Continue Watching behaviour unchanged from M3/M3.5

**What went well**

- Gate 0 → ADR → service → settings → UI cadence kept scope bounded; chapters and external subs stayed deferred.
- `PlaybackService` authority preserved — `PlayerScreen` consumes DTOs only; resume keys untouched.
- Step 5 integration audit caught platform settings gap (read-only unsupported UI) before runtime validation.
- Opt-in harness pattern (`PHASE_44_RUNTIME`) cleanly separates default CI from Windows runtime matrix.
- Non-media-backed harness scenarios (errors, settings, resume eligibility) passed under `flutter test`.

**Lessons**

- `flutter test` cannot initialise `media_kit_video` `VideoController` — Gate 0 bare `Player()` passes but app-level playback needs desktop QA or a future integration-test embedding.
- Document skipped manual scenarios explicitly; do not imply fixture-dependent or desktop-only checks ran in CI.
- Session rate vs saved default lifecycle benefits from a dedicated integration test file (`playback_integration_test.dart`).

→ [Validation results](../roadmap/m4-phase-4.4-playback-improvements.md#windows-runtime-validation-step-6--complete-commit-11b3607)

### Phase 4.5 — Performance and Caching (2026-07-16)

**What went well**

- ADR-first cadence kept scope bounded: invalidation orchestration, bounded artwork LRU, deferred search index, lazy folder tuning — no SQLite, no diagnostics UI, no search ranking changes.
- Deterministic operation-count gates (`indexBuildCount`, `cacheEntryCount`, view-prep counts) proved architectural intent without fragile wall-clock CI thresholds.
- `CatalogCacheCoordinator` centralised successful-replacement lifecycle; failed refresh semantics preserved from ADR-002.
- Opt-in harness pattern (`PHASE_45_BENCHMARK`, `PHASE_45_RUNTIME`) kept the normal suite at **556 passed / 7 skipped** while still capturing Windows runtime evidence.

**Lessons**

- Informational micro-benchmarks are useful for local comparison but must not become pass/fail gates.
- R10 scroll smoothness and live-catalogue checks (R37–R38) belong in manual release QA, not automated substitutes.
- `flutter analyze` baseline (89 findings) must be reported precisely — not as "clean".

### Live NAS catalogue — stale v2 issue (resolved 2026-07-21)

**Symptom:** Music library appeared empty or showed audio files as image entries; playback against live NAS content failed to find tracks.

**Root cause:** The app loaded a **stale catalogue** generated by scanner **v0.3.3** using **schema v2**, which did not index audio with `media_kind` or music metadata.

**Resolution:** Full rescan with scanner **v0.4.0** produced **schema v3** catalogue:

| Metric | Value |
|---|---|
| Scanner | 0.4.0 |
| Catalogue schema | v3 |
| Folders indexed | 23,042 |
| Items indexed | 121,819 |
